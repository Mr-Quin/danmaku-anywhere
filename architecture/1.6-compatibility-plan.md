# 1.6 compatibility plan: config-id identity, observable persistence, explicit dango contract

Baseline: `Mr-Quin/danmaku-anywhere` master `9ec9d3b916046a0b2def7b8814e98861d32c2ff6` (October 11, 2026). Store users are on v1.5.0 and will upgrade straight to 1.6.0. Nothing after v1.5.0 has reached a store user, so every storage version added since (Dexie v13 to v15, providerConfig v2 to v5, extensionOptions v23 to v27, danmakuOptions v8 to v10) may have its body rewritten in place. Keep the version numbers (a nightly profile at Dexie 15 would fail to open if the code's max version dropped) and reset nightly profiles instead of writing fix-up steps for them.

Companion material: the [1.6.0 release review](https://claude.ai/artifact/T3wtqZP243qouM8DEQjKF9) (findings F1 to F15, A1 to A4, N1 to N9) and the [before/after diagrams](https://claude.ai/artifact/G2PG1hFh5ryMx3ozRxZ2Nk).

## 1. Decisions

1. **Season identity is `(providerConfigId, indexedId)`.** A season belongs to the source instance that fetched it. `namespaceKey`, `identityFields`, `computeNamespaceKey`, the runtime reconciler and the `seasonsReady()` gate are removed. The row keeps `manifestId` for provider type, chips and filters.
2. **Deleting a source keeps its seasons viewable as orphans.** Re-adding a custom source gets a new id and does not reattach automatically. A later UI action ("attach orphaned seasons to this source", sets `providerConfigId` on chosen rows) covers re-add and cross-device cases. Built-ins have stable ids (`id === manifestId`) and reattach by construction.
3. **Dango owns execution and output shape, not identity.** `identityFields` leaves the manifest schema. Dango exports the schemas for what a pipeline must emit and validates its own manifests against them in CI. A dango tag's manifests are tested against that tag's engine; the extension refuses a catalog whose `packageVersion` is newer than its bundled engine.
4. **Persistence failures are observable.** A failed storage read is distinguishable from an absent key; a failed write never reports success; the options upgrade never resets a store because of an I/O error; `lastVersion` advances only when every store persisted.
5. **No new frameworks.** No startup coordinator, event bus, repository layer or migration plugin system. Keep Dexie transactions, `ManifestRegistry`, `ManifestProviderService`, the options services and the versioned migration functions.
6. **Not changed:** source-deletion semantics (orphans stay viewable); the policy that a shorter refetch keeps the larger stored comment set; the backup envelope; the seed flag and seeding flow; the built-in `id === manifestId` rule.

## 2. Invariants (acceptance criteria for every work package)

1. A failed storage read is distinguishable from an absent key. A failed write never reports successful persistence.
2. Transforming or validating a backup performs no writes, network calls or runtime service mutations.
3. Historical migration functions produce their historical target shape, independent of current converter behaviour.
4. Season identity is `(providerConfigId, indexedId)`, unique. Episode identity is `(seasonId, indexedId)`, unique.
5. A season row always carries `manifestId` and `providerConfigId`. A row whose `providerConfigId` matches no live config is an orphan: readable, not refetchable, relinkable.
6. No Dexie upgrade reads Chrome storage. No Dexie upgrade rewrites `episode` or `customEpisode` rows unless the schema of those rows changes.
7. A failed prerequisite never becomes a successfully memoised result.
8. Local rendering of downloaded comments needs no network access and no catalog refresh.
9. The upgrade orchestration is restartable without guessing which stores persisted.
10. The extension validates every value that crosses the dango boundary (manifest, catalog index, pipeline output) with a schema that dango exports or the extension owns; TypeScript casts are not validation.

## 3. Ownership after the changes

| Concern | Owner | Boundary |
|---|---|---|
| Manifest schema, pipeline execution, output row contracts | dango | Exports `zManifest`, `SUPPORTED_API_VERSIONS`, and the output row schemas. Knows nothing about extension storage, config ids or local database ids. |
| Catalog compatibility | dango CI + `ManifestRegistry` | Dango tests a tag's manifests against that tag's engine. The extension applies a catalog only when `catalog.packageVersion` is not newer than the bundled engine version. |
| Raw pipeline output to extension entities | `ManifestProviderService` | Parse with dango's row schemas, strip HTML, stamp `manifestId` + `providerConfigId` + `schemaVersion`. |
| Season identity and orphan handling | `SeasonService`, `resolveSeasonConfig` | Lookup by `providerConfigId`; orphans are rows whose config is gone. |
| Historical shape translation | Versioned migration functions | Pure input (plus context) to output. No live service calls. |
| IndexedDB structure | Dexie versions in `db.ts` | Row-local transforms only. |
| Configuration persistence | `ExtStorageService`, `OptionsService` | Explicit success or failure. No defaults on I/O failure. |
| Upgrade ordering and completion | `OptionsManager`, `UpgradeService`, `ReadinessService` | `lastVersion` is the options marker; written only on full success. |
| Backup preparation and selective commit | `ConfigStateService` | Prepare and validate everything, then commit each store, report each outcome. |
| Catalog fetching and installed runners | `ManifestRegistry` | Offline bundle initialisation independent of catalog availability. One replacement path. |

### WP2: observable persistence failures (DA-720, extension)

Branch `DA-720_storage-failures-observable`. Rebases on WP1 before review. Keep changes to `ProviderService.ts` and `ManifestRegistry.ts` minimal and in their own commit to ease the rebase.

**Goal.** Invariants 1, 7 and 9. A storage error is an error, never defaults and never success.

**Files (relative to `packages/danmaku-anywhere/src`).**

- `common/storage/ExtStorageService.ts`: `read()` rejects on API failure and returns `undefined` only for an absent key; `set()`, `delete()`, `clearStorage()` reject on failure and notify subscribers only after success. Remove the internal `Logger.error` swallow; callers log where they have context.
- `common/options/OptionsService/OptionsService.ts`: `upgrade()` reads (a read error propagates), decides absent-vs-present, computes the migrated value inside the invalid-data `try` (a thrown migration still resets, preserving today's recovery policy), then persists **outside** that `try` so a write error propagates. Add `readStoredUnblocked(): Promise<Options<T> | undefined>` returning the raw versioned envelope; `readUnblocked()` keeps returning defaults for existing callers. `set()`/`update()` propagate storage errors to the caller.
- `background/syncOptions/UpgradeService/UpgradeService.ts`: gather context with `readStoredUnblocked`; run each store's `upgrade()`; if any store rejected, do **not** write `lastVersion` and do not call `setReady()`; rethrow an aggregate error listing the failed stores. `OptionsManager.ts`: on failure clear the memoised `upgrading` promise so the next install/startup/wake event starts a fresh attempt; catch and log the fire-and-forget calls (`upgradeIfVersionChanged`, the `onInstalled` body). `isCurrentVersion()` read failure is an error and triggers one upgrade attempt, never a reset.
- `common/options/ReadinessService/ReadinessService.ts`: leave the pending/ready promise as is in this package (the failed state and cross-context status RPC are WP7). Only make `init()` and `setVersion()` propagate read/write errors to their callers.
- `background/services/Backup/ConfigStateService.ts`: a rejected `options.set` already lands in the per-store `catch`; keep that and make sure the error message is the storage error. `getState()` fails on a read error rather than exporting defaults or version 0.
- `background/services/providers/ManifestStore.ts` and `ManifestRegistry.ts`: `setMany`/`remove` reject on failure; `saveUserManifest`, `fetchAndStore`, `seedFromBundle` and `unregister` update the in-memory `runners` only after the store write resolved. `init()` must not turn a failed `getAll()` into `{}` and re-seed the bundle: let `ready` reject, and log once at the `ProviderService.setup()` call site.
- `background/services/providers/ProviderService.ts`: `runSeedDefaultProviders` writes configs, then the flag; a failed config write leaves the flag unset. `localizeLegacyBuiltinNames` propagates.
- `common/options/providerConfig/service.ts`: `hasSeeded`/`markSeeded` propagate.
- Popup: `common/storage/hooks/useSuspenseExtStorageQuery.ts` (and the `useOptions`-style hooks built on it) await the UI container's `ReadinessService.waitUntilReady()` before the first read of any option store key, so a popup opened mid-upgrade suspends instead of rendering old-shape data. Keys that are not option stores (e.g. `manifests`) are unaffected.

- `ManifestRegistry.test.ts`: `saveUserManifest` rejects when the store write fails and `getRunner(id)` still throws; `init()` with a failing store rejects `ready`.

## 7. Human gate and release checklist

Before each PR is opened the maintainer reviews the branch summary. Before the tag:

- Fresh install online and offline.
- Real v1.5.0 profile upgrade (e2e migration suite) including the self-hosted season keeping its uuid and exact saved comment counts.
- The pre-v10 database fixture.
- Real v1.5.0 backup restore and export/restore/re-export equality.
- Interrupted configuration commit followed by worker restart.
- Catalog recovery, user-manifest edit, bundled-to-catalog update.
- Two configs for one server produce two seasons; deleting one leaves the other's bookmarks.
- Source deletion with downloaded comments and bookmarks; built-in re-add reattaches; custom re-add orphans (until relink).
- Production artifact with valid proxy variables and the actual release version.

Release notes may promise validation before restore writes and preservation of existing data when a candidate is rejected. They must not promise atomic restore across stores or automatic reconnection of a re-created custom source.

## 8. Known limitations after this plan

- A deleted and re-created custom source does not reattach its seasons until the relink action ships. Seasons stay viewable.
- Two custom configs pointing at one server keep separate caches. That is the model: an instance is a source.
- Restore is per store, not atomic across Chrome storage and IndexedDB; outcomes are reported per store.
- Nightly profiles that already carry `namespaceKey` rows must be reset; no fix-up step is written for them.
